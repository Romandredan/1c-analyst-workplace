# Analyst Handoff

Пакет аналитика нужен, чтобы адресат понял проблему, выбранные решения и свой
следующий шаг без восстановления всей истории обсуждений. Заказчику нужен
документ на подпись. Разработчику нужна проверенная спецификация и связи от
решения до задачи.

Навык стоит в конце цепочки и ничего не изобретает сам:

```text
сырьё и встречи → извлечение требований → ответы заказчика → ADR и прожарка
  → пакет для заказчика (подпись) → изменение OpenSpec → пакет для разработки
```

Скрипты лежат в папке навыка (`<папка-навыка>/scripts/`), пакеты лежат в
проекте. В командах ниже `<навык>` означает путь к папке навыка, а пути
`deliverables/...` отсчитываются от корня проекта.

## Выбор режима

| Запрос | Режим | Формат |
|---|---|---|
| Согласовать с заказчиком по шагам: текст, потом диаграммы, потом экраны | Заказчик, итерационный | [customer-package.md](customer-package.md) |
| Подготовить заказчику полный документ за один запуск | Заказчик, полный | [customer-package.md](customer-package.md) |
| Передать в разработку, проверить готовность к реализации | Разработка | [dev-package.md](dev-package.md) |

Если неясно, кто адресат, спроси. Если неясно, итерационный или полный режим,
выбери итерационный: его можно продолжить, полный нельзя разрезать после запуска.

## Жёсткие границы

- Не пиши код и не вызывай `openspec-apply`.
- Не создавай mock API и не вызывай внешние системы.
- Не принимай решения за владельца. `Подтверждено` в пакете для заказчика и
  `accepted` в ADR ставь только после явного подтверждения человека.
- Не выдавай открытые вопросы за согласованные решения.
- Не используй эталон как исходник без явного разрешения. Эталон - это готовый
  ответ на работу этого навыка: целевой документ, подписанный пакет, решение из
  другого проекта. Он нужен для проверки, а не для скрытого пересказа.
  Результаты предыдущих шагов цепочки (извлечение требований, ответы, ADR)
  являются входами, а не эталоном.
- Не заполняй раздел без источника. Раздел, для которого нет фактов, решений или
  ответов, становится строкой открытых вопросов с адресатом.
- Не пиши требования, сценарии и задачи вместо OpenSpec. Их место в
  `openspec/changes/<change-id>/`, пакет на них ссылается.

## Режим: заказчик

### Входы

Найди и перечисли в манифесте пакета:

- исходную постановку и сырьё (письма, расшифровки встреч);
- результат извлечения требований и ответы заказчика;
- ADR, включая предложенные (`proposed`);
- итог прожарки решений, если она была;
- результаты проверок данных и конфигурации, если они были.

OpenSpec для этого режима не нужен: согласование с заказчиком идёт до
спецификации для разработки.

### Пакет

Пакет живёт в `deliverables/<case-id>/customer/`. Текст находится в одном файле
`package.md`: это единственный источник правды, диаграммы и экраны строятся из
него. Профиль по умолчанию: итерационный режим - краткий, полный режим - полный.
Пользователь может выбрать другой, профиль записывается в манифест.

### Проходы

| Проход | Что делается | Результат |
|---|---|---|
| 1. Текст | `package.md` по разделам профиля, заглушки `D<N>` и `S<N>` на местах будущих картинок, манифест, `CHANGELOG.md` | `package.md`, `README.md` |
| 2. Диаграммы | Для каждой `D<N>`: исходник `.mmd`, рендер Mermaid CLI (`mmdc`), просмотр картинки, картинка под заглушкой | `diagrams/` |
| 3. Экраны | Для каждой `S<N>`: прототип формы навыком прототипирования экранов (например, md-design-prototype), картинка под заглушкой | `screens/` |
| 4. Сборка | `python <навык>/scripts/build_package.py deliverables/<case-id>/customer` ([scripts/build_package.py](scripts/build_package.py)) | `build/*.docx`, `build/*.html` |
| 5. Правки | Замечания заказчика вносятся в `package.md`; по колонке «Основано на» манифеста перестраиваются затронутые D и S; версия растёт; запись в `CHANGELOG.md`; повтор сборки | Новая версия |

После каждого прохода запусти
`python <навык>/scripts/check_package.py customer deliverables/<case-id>/customer`
([scripts/check_package.py](scripts/check_package.py)) и исправь ошибки до
отчёта.

Правила проходов:

- Проход начинается с чтения манифеста. Если пользователь не назвал проход,
  выполни следующий по манифесту.
- Если диаграмма или экран показали пробел в тексте, останови проход, предложи
  правку текста и дождись решения. Картинку под текст не подгоняй.
- Если инструмента прохода нет (Mermaid CLI, навык прототипирования, pandoc),
  остановись и назови, что установить. Пользователь может отметить проход в
  манифесте как `не требуется`.
- Сборка с кодом выхода 2 означает: HTML собран, DOCX нет, pandoc не найден.
  Сообщи об этом, а не об успешной сборке.

### Итерационный режим

Один запуск выполняет ровно один проход. После прохода обнови манифест, сообщи,
что создано, какие пробелы найдены и какой проход следующий, и остановись.
Следующий проход не начинай, даже если он кажется очевидным и быстрым:
пользователь смотрит на результат каждого прохода, в этом смысл режима.

### Полный режим

Проходы 1-4 выполняются подряд за один запуск. После каждого прохода выполни
проверку из [review-checklist.md](review-checklist.md), раздел «Пакет для
заказчика», и `check_package.py customer`. Если проверка не пройдена,
остановись на этом проходе и сообщи причину. После прохода 4 остановись на
приёмку человеком. Проход 5 всегда запускается отдельно.

### Открытые вопросы и адресат

В пакет для заказчика попадают только вопросы, на которые отвечает заказчик или
владелец риска (бухгалтерия, служба безопасности). Технические вопросы
реализации идут в манифест (краткий профиль) или в разделы 8-9 (полный профиль).

Если после извлечения требований, ответов и прожарки вопросов к заказчику не
осталось, раздел 11 содержит строку «Открытых вопросов нет». Больше пяти
вопросов к заказчику означает пропущенный шаг: перечисли их и предложи вернуться
к извлечению требований до отправки пакета.

## Режим: разработка

Этот режим проверяет и связывает готовые артефакты. Он не пишет вторую
спецификацию.

### 1. Входы

Обязательны:

- изменение OpenSpec `openspec/changes/<change-id>/` с `proposal.md`,
  `tasks.md` и спецификациями требований;
- пакет для заказчика или ADR, из которых видно, какие решения подтверждены.

Если изменения OpenSpec нет или `openspec validate <change-id> --strict` не
проходит, остановись. Назови пропущенный шаг (создать изменение OpenSpec по
пакету для заказчика, например навыком openspec-propose) и перечисли, что
должно в него войти. Требования, сценарии и задачи сам не пиши.

### 2. Покрытие

Сверь смысл, который строгая валидация OpenSpec не проверяет:

- каждое подтверждённое решение Р-N покрыто требованием;
- у каждого требования есть основной и отказный сценарий;
- каждая задача связана с требованием;
- для каждой внешней интеграции в `design.md` есть триггер, данные, ошибки,
  повторы и владелец;
- открытые вопросы не блокируют реализацию или вынесены в блокеры.

Найденный пробел записывается в `handoff.md`, раздел «Замечания к артефактам»,
с владельцем. Исправляет его владелец артефакта, а не этот режим: файлы OpenSpec,
пакета для заказчика и ADR не правь. Какие замечания блокируют реализацию,
определено в [dev-package.md](dev-package.md), раздел «Блокеры». Скрипт
проверяет число сценариев, но не их смысл: что один из сценариев отказный,
проверяй чтением.

### 3. Пакет

Создай `deliverables/<case-id>/dev/` по [dev-package.md](dev-package.md):
`README.md` (карта и вердикт), `traceability.md` (цепочка от источника до
задачи), `handoff.md` (границы, порядок, остаточные риски).

### 4. Проверка

```bash
openspec validate <change-id> --strict --json --no-interactive
python <навык>/scripts/check_package.py dev deliverables/<case-id>/dev --change <change-id> --customer deliverables/<case-id>/customer
```

Обе команды запускай из корня проекта: `check_package.py dev` ищет
`openspec/` в текущей папке (или в папке, переданной в `--root`). Проверяй
фактический результат. Не сообщай об успехе по одной команде запуска.

### 5. Финал

Вердикт «готово к реализации» ставится, только если блокеров нет и проверки
пройдены. Иначе вердикт «не готово» и список блокеров с владельцами. Остановись
на приёмку человеком. Не переходи к реализации.

## Инструменты

| Задача | Инструмент |
|---|---|
| Проверка объектов конфигурации | `code-index` или другой индекс кода, только чтение |
| Диаграммы | Mermaid CLI (`mmdc`), навык диаграмм Mermaid |
| Прототипы экранов | Навык прототипирования форм (например, md-design-prototype) |
| Сборка DOCX и HTML | `scripts/build_package.py` (pandoc; без него только HTML) |
| Проверка пакетов | `scripts/check_package.py customer` и `dev` |
| Спецификация | OpenSpec CLI, `openspec validate --strict` |
| Приёмка решений и рисков | Человек |

Полный перечень проверок: [review-checklist.md](review-checklist.md).

## Типичные ошибки

| Ошибка | Как правильно |
|---|---|
| Пакет для заказчика собран в формате для разработки: десятки требований и кодов | Один `package.md` по профилю, язык заказчика |
| Технические вопросы (протоколы, повторы, тестовые контуры) отправлены заказчику | Они идут в манифест или разделы 8-9 |
| Под картинку оставлено «будет потом» без заглушки | Заглушка `<!-- D1: ... -->` и видимая подпись, запись в манифесте |
| Диаграмма нарисована «как должно быть», хотя текст этого не говорит | Сначала правка текста, потом картинка |
| Без OpenSpec в режиме «разработка» сочинены требования и сценарии | Остановка и имя пропущенного шага |
| `Подтверждено` поставлено по выводу из встречи | Только после явного подтверждения человека |
